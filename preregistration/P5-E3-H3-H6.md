# Pre-registration P5, part 1: the referee study (E3) with H3 and H6

Registered by the commit that adds this file (its timestamp is the registration); the file's SHA-256 is published on
Kaggle the same day. Written 2026-10-04, before any in-task referee verdict has been computed or looked at. Analyses
that are not listed here are exploratory and are reported as such. Outcomes are reported next to these predictions,
including those that contradict the thesis (F19).

## Objects
- **Patch pool.** Every non-empty patch produced by any agent arm on a dev-split task in a ledger-recorded run of the
  development referee (kernels/rollout/rollout.py; any candidate, any replicate) up to the paper freeze (2026-11-05).
  Holdout tasks are never used. Empty patches are excluded (no referee can judge them; they are counted separately).
- **Truth.** Y = 1 when the patch resolves the task under the hidden tests as graded by the development referee
  (`resolved` in the run's task_results.jsonl, the field the ledger reads). Base rate p = mean Y over the pool.
- **Referees** (each returns accept or reject for one patch):
  - R-self: the agent's own claim in its context: accept when its final message or its last verdict line asserts that the
    fix works (for candidates that print a structured verdict line, that line; otherwise the rule frozen in the
    configuration commit below, applied mechanically to the trace);
  - R-repro: the agent's own reproduction test: accept when its last execution after the last edit to a source file exits
    0; undefined (excluded from R-repro's estimates, counted) when the agent wrote no reproduction test;
  - R-fresh: an independent judge: one call to the same model (gemma-4-31b-it-qat-w4a16-ct, same serving settings) in a
    fresh context holding the issue text and the patch, returning accept or reject under a fixed prompt;
  - R-near: nearby existing tests: the repository's own tests closest to the changed code, run on the patched code in the
    same sandbox, excluding every file of the hidden test patch: accept when none fails that passed before the patch.
  The R-fresh prompt, the R-self rule and the R-near selection heuristic are frozen by a dated amendment commit to this
  file before the first judging run; no verdict is computed before that commit.

## Quantities (metric M4)
For each referee r: sensitivity alpha_r = P(accept | Y=1), false acceptance beta_r = P(accept | Y=0), LR_r =
alpha_r / beta_r, posterior q_r = p alpha_r / (p alpha_r + (1-p) beta_r). 90% Wilson intervals for alpha and beta;
90% intervals for LR and q by a task-clustered bootstrap (resampling tasks, 2,000 draws, seed 20261004).

## Predictions and tests
| id | quantity | prediction under H-Sys | prediction under H-Mono | analysis | threshold |
|---|---|---|---|---|---|
| E3-a | LR_r for each referee | every in-task referee is informative, LR_r > 1; executed referees beat judgement: LR(R-repro) and LR(R-near) exceed LR(R-self) | judgement in context is as good as execution: LR(R-self) not below the executed referees | per-referee LR with task-clustered 90% bootstrap intervals | informative: the lower 90% bound of LR_r exceeds 1; ordering: the 90% interval of LR(R-repro)/LR(R-self) (and of R-near/R-self) lies above 1 |
| H6 (E2) | escaped errors (wrong patches accepted) under R-fresh vs R-self | independence catches errors self-judgement misses: beta(R-fresh) < beta(R-self) | no independence benefit: beta(R-fresh) >= beta(R-self) | exact one-sided McNemar on wrong patches judged by both (discordant pairs: self accepts and fresh rejects, vs the reverse) | H6 supported when p < 0.10 in the predicted direction; refuted when escaped errors do not fall (the paper's registry, H6) |
| H3 (Prop. 1) | success of best-of-n selection with referee r among a task's candidate patches, for n in {2, 3} (and larger n where the pool allows) | the observed curve follows Prop. 1 computed from the measured (alpha_r, beta_r) and each task's own base rate, and plateaus near q | (not a sys/mono contrast; a test of the selection model) | per task t with at least n patches: draw n of its patches without replacement (all subsets when few), select uniformly among accepted ones (all if none accepted), average success over subsets and tasks; prediction: the same average of P_n(p_t, alpha_r, beta_r) with p_t the task's pool rate; intervals by task-clustered bootstrap | H3 supported when each observed P_n lies inside the 90% interval of the prediction; refuted when the observed plateau exceeds the predicted q beyond its 90% interval (the paper's registry, H3) |
| E3-b | the bound of Prop. 2 | the observed selection lift never exceeds p (LR - 1) beyond its 90% interval | (same) | as H3 | violation is reported as evidence of correlated verdicts (the propositions assume conditional independence) |

## What would change the main track
If an in-task referee with LR well above 1 exists at a cost the per-task budget can pay, AXI-mini uses it to choose among
candidates (main-05, main-06); if none does, selection inside the task is dropped in favour of generation-side changes.

## Power (planning, not a claim)
A first dev session yields on the order of 150 non-empty patches; at a resolve rate near 0.2 that is roughly 30 correct
and 120 wrong ones: alpha within about +-0.15 and beta within about +-0.07 (90%). The pool grows with every dev run until
the freeze; the final counts are reported.

## Amendments (dated, appended below; each before the run it governs)

### A1 (2026-10-06): the frozen referee rules
Written before any referee verdict on the pool has been computed or looked at; the rules were set from the agents'
prompts and the trace schema (ATIF v1.7: steps[].tool_calls with full arguments, observations carrying status and, for
run_command, exit_code), not from outcomes. Every rule below is applied mechanically by committed code; any later change
is a new dated amendment made before the run it governs.

- **Pool rows.** One row per (run, arm, replicate, task) of a ledger-recorded dev run whose agent patch is non-empty;
  gold arms are not agent arms and are excluded. Y is that row's `resolved`.
- **R-self.** Accept when the trace contains an explicit `submit_patch` call whose observation has status "ok" (the agent
  declared its fix complete; its final message is written after that call). Reject otherwise, including a session that
  ended by timeout with a working-tree patch collected by the harness. For a candidate that prints a structured verdict
  line (a line starting with `AXI_VERDICT`), the last such line in any tool output or message decides instead: PASS
  accepts, anything else rejects.
- **R-repro.** A reproduction test is a .py file the agent created during the task (by `write_file`, or by a
  `run_command` that writes it through a heredoc or a redirect) and later ran with python or pytest in a `run_command`
  whose command names that file. A source edit is any `edit_file` or `write_file` on a file under the repository that is
  not one of those reproduction files. Accept when the last run of any reproduction test after the last source edit has
  exit_code 0; reject when it is non-zero or the call timed out; undefined (excluded from R-repro's estimates, counted)
  when no reproduction test was run after the last source edit.
- **R-near.** Changed files are the .py files under the repository that the agent patch modifies outside test
  directories. Candidate test files are the snapshot's existing test files (under a directory named tests or test, or
  named test_*.py or *_test.py), excluding every file the task's hidden test patch touches, that either have a basename
  containing a changed module's stem (rank 1) or import a changed module by its dotted path or as `from <package>
  import <stem>` (rank 2); ties by path; at most 5 files. They run as `python -m pytest -q -p no:cacheprovider
  --junitxml=<file> <files>` with a 120 s limit, once on the snapshot and once with the agent patch applied, in the
  development referee's sandbox. Accept when no test case that passed before fails or errors after; reject otherwise;
  undefined (counted) when there is no candidate file, the first run collects no test, or either run hits the limit.
- **R-fresh.** One request per pool row to the same served model with the rollout kernel's server settings and the
  agent's sampling (temperature 0.2, top_p 0.95, thinking budget 4096 with thoughts included, max_output_tokens 8192),
  no tools, fresh context, the issue text from the task record and the agent patch as a unified diff; a patch longer
  than 60,000 characters is cut there with the line `[patch truncated]`. The prompt is exactly:

  > You are reviewing a proposed change to a Python repository. You did not write it.
  >
  > Issue:
  > {issue}
  >
  > Proposed patch (unified diff):
  > {patch}
  >
  > Decide whether this patch resolves the issue completely and correctly without breaking existing behaviour. Check
  > the exact behaviour, names, messages and edge cases the issue asks for. You cannot run code.
  >
  > End your answer with exactly one line: VERDICT: ACCEPT or VERDICT: REJECT

  The verdict is the last line matching `VERDICT: (ACCEPT|REJECT)` in the visible answer. A response without one is
  retried once with the same prompt; if it still has none, the row is undefined for R-fresh (counted).
- **Undefined rows** are reported per referee and never imputed. H6's McNemar uses wrong patches with both R-self and
  R-fresh defined; H3 and E3-b use each referee's defined rows.

### A2 (2026-10-06): how A1's trace rules read the real trace format
Written before any verdict on the pool; it settles points A1's text leaves open, learned from the trace schema only.
- A source edit is an `edit_file` or `write_file` call whose observation has status "ok"; a call that failed did not
  change the file and does not move "the last source edit". A reproduction file is created only by a `write_file`
  with status "ok" or by a `run_command` heredoc or redirect (write_file outside the workspace fails, so most
  reproduction files appear through run_command).
- A `run_command` that creates a reproduction file and runs it in the same command counts as a run after its creation.
  Heredoc bodies are not searched for runs or redirects.
- "Names that file": a token with a directory must match the file's path; a bare file name matches by basename (for
  `cd /tmp && python r.py`). Paths under the repository are relative ones or ones under /workspace.
- Exit codes: a non-zero run_command comes back as status "error" (CommandError) with exit_code in its details; a run
  with error_type TimeoutExceeded, or with no observation, counts as timed out (reject).
- When one step holds several tool calls and one observation, the observation belongs to the first call of the tool it
  names. Calls whose file argument is missing or malformed name no file and are ignored by both rules.
- AXI_VERDICT lines are read from agent messages and tool outputs (never system or user steps or call arguments); after
  leading whitespace, only the word PASS (optionally after ":" or "=") accepts.
- Reporting: an LR with beta = 0 is reported as infinite (no smoothing); H6 is supported only when p < 0.10 and the
  discordant count favours R-fresh (b > c); E3-b reports both the point violation and whether the lift interval's lower
  end lies above the bound.

### A3 (2026-10-06): R-near validity and readings
Written before any R-near verdict. The build found that in the referee's subprocess sandbox a src-layout package that
is also installed in the kernel's Python is imported from the installed copy, not from the workspace, so tests there
cannot see the patch. The hidden-test truth is unaffected for pool tasks (a dev task is sound only if the reference
fix passes and an empty patch fails, which requires the grader to import the workspace), but R-near needs its own check.
- **Validity.** After setup and before the first run, each changed module is imported in the sandbox with the
  environment the tests use and its `__file__` is read; if any resolves outside the workspace, the row is undefined for
  R-near (counted as "environment cannot see the patch"). A changed `__init__.py` stands for its package.
- **Readings.** A test case that passed before and is missing after the patch counts as failing (a collection error
  removes every case). A patch that does not apply, or an exception in the runner, makes the row undefined (counted).
  `conftest.py` and `__init__.py` files are never candidate test files. Changed files exclude test directories only.
  The run on the snapshot may be reused for rows of the same task with the same candidate files.
- **R-fresh prompt text.** Trailing newlines of the issue and of the patch are dropped before they are inserted, so
  the blank lines of the template are kept; the 60,000-character cut applies to the patch as inserted. A request the
  server refuses (prompt plus output above the context) is a response without a verdict (one retry, then undefined).

### A4 (2026-10-06): analysis readings, fixed after the instrument review and before any analysis of the pool
The first review of the offline instrument ran the trace referees blind (no outcome read, no analysis run) and found
analysis steps that P5 implies but the code did not compute. These readings are fixed before any analysis output exists.
- **One bootstrap for all referees.** Each of the 2,000 draws (seed 20261004) resamples, with replacement, the pool's
  tasks (every task with at least one pool row); every referee's quantities in a draw use its defined rows within the
  drawn tasks. A draw in which a quantity is undefined (no positives, no negatives, or alpha = beta = 0 for LR) is
  dropped for that quantity only, and the number of dropped draws is reported. Percentile intervals (5th, 95th).
- **E3-a.** "Informative" means the lower 90% bound of LR_r exceeds 1. The ordering intervals are those of the ratios
  LR(R-repro)/LR(R-self) and LR(R-near)/LR(R-self) computed within each draw.
- **p and q.** For each referee, p is the mean Y over that referee's defined rows (A1 excludes undefined rows from a
  referee's estimates), and q_r is computed from that p.
- **H3.** n runs over 2 and 3, and over larger n only while at least 10 tasks have n or more defined rows; at most 200
  subsets per task (all when fewer; otherwise a seeded sample). "Refuted" means the observed P_n at the largest n
  exceeds the upper 90% bound of the predicted plateau, the mean over the same tasks of q(p_t); "supported" means every
  observed P_n lies inside its prediction's 90% interval; otherwise "inconclusive".
- **E3-b.** Prop. 2 holds per task (P_n - p_t <= p_t (LR - 1)), so the averaged bound is mean(p_t)(LR - 1) over the
  same eligible tasks as the lift, both with the same bootstrap draws; a violation is reported when the lift's lower
  90% bound exceeds the bound's upper 90% bound, and the point comparison is reported too.
- **H6.** "Supported" when p < 0.10 and b > c; "refuted" when b <= c (escaped errors do not fall); otherwise
  "inconclusive".
- **Rows.** The pool takes ledger run rows on the dev split only and refuses any task outside the dev split; a row
  without a resolved field is an error, not Y = 0. A row without a trace is undefined for the trace referees. A
  write_file counts as creating a file only if the trace shows no earlier successful read or edit of that path. An
  AXI_VERDICT line is "AXI_VERDICT", optional spaces, an optional ":" or "=", spaces, then the verdict word.
- **Exit codes.** R-repro reads the exit code of the whole run_command, as A1 states; commands that pipe the
  reproduction run into another program report the pipe's exit code. This is reported as a limitation with its count.

### A5 (2026-10-06): R-near and R-fresh readings after the kernel review, before any R-near or R-fresh verdict
- **Nothing to protect.** R-near is undefined when no test case passed in the run on the snapshot (cases that are only
  collection errors or failures leave nothing a patch could break).
- **One configuration.** Both R-near runs follow the grader's test refresh before running (test dependencies installed
  and the harness's hermetic pytest configuration written over the repository's), so a difference between the runs
  can only come from the patch.
- **Hidden test files** are those in the task's test_files plus every file the hidden test patch touches.
- **Validity probe.** A changed module that cannot be imported is located through its nearest importable parent
  package; if no level imports, or the probe returns no report, the row is undefined ("environment cannot see the
  patch"). setup.py, conftest.py and noxfile.py are never changed modules. A changed `__init__.py` stands for its package
  for both the probe and rank 1's stem.
- **Runner failures.** An after-run that leaves no junit report is undefined, not a reject. Patch files are read as
  UTF-8 with replacement; a patch that then does not apply is undefined (A3).
- **R-fresh verdict line.** The verdict is the last line of the visible answer that, after stripping whitespace and the
  characters * ` _ from both ends, equals "VERDICT: ACCEPT" or "VERDICT: REJECT"; a line that names both or adds words
  is not a verdict line.
- **Limits and sessions.** Each R-fresh attempt has a 300 s wall-clock limit; a timed-out attempt is a response
  without a verdict (one retry, then undefined). A kernel run may take a contiguous range of pool rows and skip keys
  already judged in an attached earlier output; the verdict set is the union, and a key judged twice keeps its first
  complete verdict.

### A6 (2026-10-06): last readings before any analysis, R-near or R-fresh verdict
- H3: when both "refuted" and "supported" hold, "refuted" is reported. Where q(p_t) is undefined (the referee accepts
  nothing on that task's mix), the task's plateau is p_t, the limit of Prop. 1.
- R-self: only lines matching A4's AXI_VERDICT pattern are verdict lines; any other line beginning with AXI_VERDICT is
  ignored and R-self falls back to the submit_patch rule.
- R-near mirrors the grader's reset of protected files exactly, including its behaviour when a listed path is absent
  from the repository (the reset then restores nothing, so an agent's edit to an existing test file stays in both the
  grader's run and R-near's after-run).

### A7 (2026-10-06): R-near probe scope, before any R-near verdict
The third instrument review counted, blind, 15 of 182 pool rows whose patch adds a new top-level .py file (an agent's
scratch script); under A5 the probe called them blind, although the workspace root is on the import path.
- The validity probe checks changed files that exist in the snapshot, and new files inside an existing package through
  that package. A new file with no existing package above it is not probed (no installed copy can shadow a module the
  snapshot lacks); if it is the only changed file, the row goes on to test selection as usual.
- Between the run on the snapshot and applying the agent patch, the workspace returns to its baseline commit, so the
  patch applies to the same tree as in the grader; the grader's refresh then runs before the second run (A5).

### A8 (2026-10-06): R-fresh time limit and batching, before any R-fresh verdict
Agent traces show about 34 output tokens per second for one request on the served model; a maximal answer (8,192
tokens) would take about 240 s alone and longer when requests share the server. To run the judge within the quota, up
to 4 requests run at a time, and each attempt's limit is 600 s (replacing A5's 300 s). Verdicts do not depend on the
order or the batching of requests; everything else in A1, A3 and A5 is unchanged.
